# piki-core

UI-agnostic library crate. **Must NOT depend on `crates/tui` or `crates/api-client`.**

## Modules

- `chat.rs` — `ChatMessage`, `ChatRole` (System, User, Assistant, Tool), `ChatConfig`, `ChatServerType`, `ToolDefinition`, `ToolCall`, `ToolResult` — domain types for the global AI chat panel with tool-use support. `ChatServerType` enum (Ollama, LlamaCpp, OpenRouter) selects which server backend to use. `ChatMessage` has optional `tool_calls` and `tool_call_id` fields for agentic tool-use flow. Used by both TUI and Desktop frontends.
- `domain.rs` — `AIProvider` (with `Custom(String)` variant), `WorkspaceInfo`, `WorkspaceType` and other shared types. Re-exported from `lib.rs`.
- `providers.rs` — `ProviderConfig`, `PromptFormat`, `ProviderManager` — user-configurable providers loaded from `providers.toml`. Manages custom provider binaries, args, prompt format, and agent directories.
- `app_settings.rs` — The settings both frontends honour without `config.toml`: `AppSettings { sessions_enabled, notification_delivery, sound }` (all `Option`, `None` = follow the file) stored as JSON under `ui_preferences.app_settings`; `resolve(config_path, ui_prefs) -> EffectiveSettings` is the ONE merge (**database override > `config.toml` > default**, unit-tested) — TUI `App::new` folds it into `Config` (`sessions.enabled`, `notifications`), the desktop's `main.rs` reads it before `connect_session_daemon` / `NotificationsConfig::apply`, and `commands/settings.rs::set_app_settings` writes it. Add an overridable key here (field + `notifications()`/`sessions_enabled()` merge + tests), never a second pref key.
- `storage/` — Trait-based storage layer. Traits in `mod.rs` (`WorkspaceStorage`, `ApiHistoryStorage`, `UiPrefsStorage`, `AgentProfileStorage`), SQLite backend in `sqlite.rs`, legacy JSON in `json.rs`.
- `workspace/` — Git worktree CRUD (`WorkspaceManager`), `FileWatcher` (notify crate), config persistence.
- `pty/` — `PtySession` wrapping `portable-pty` with `spawn_blocking` for non-blocking reads, `vt100::Parser` for terminal state. The reader optionally feeds bytes through `shell_integration::parser::OscParser` and updates per-session `ShellSession` state (cwd, last command exit code). The vendored vt100 queues responses to terminal query sequences (DSR `CSI 6n`/`CSI 5n`, DA1) in `Screen::take_answerback()`; the reader drains that after each parse pass and queues it for the PTY — apps that probe the terminal at startup (muse, vim) hang or silently exit without it. **All writes to the master go through a per-session `pty-writer` thread** (`PtySession::write` only enqueues): a direct `write(2)` blocks once the kernel's ~4 KiB input queue fills, which froze the UI thread whenever a child stopped reading stdin, and could deadlock outright when the reader thread blocked on an answerback write and stopped draining the child's output. Pinned by `tests/pty_session.rs::test_write_never_blocks_when_child_ignores_stdin`. Pinned by `tests/vt100_answerback.rs` (unit) + `tests/pty_terminal_queries.rs` (ignored E2E, drives real `muse`).
- `shell_integration/` — Init scripts (zsh, bash) embedded via `include_str!`, `OscParser` (streaming OSC 133/7 state machine), `install` module that detects shell family and prepares env vars + extra args (`ZDOTDIR` / `--rcfile`) so the user's shell sources our bridge before its real dotfiles. Linux/macOS only.
- `cli_agent/` — Structured agent lifecycle channel: `CliAgentEvent`/`CliAgentState` (the shared protocol both frontends render), `sock` (per-tab FIFO reader), and one install module per agent whose hooks we bridge. `bridge_for_command()` maps a provider's binary to its bridge and is the **only** place that decides whether a tab gets the structured channel — never re-hardcode `cmd == "claude"` at a spawn site. `install` (Claude Code) passes a generated hook config via `claude --settings`, so it's per-spawn and touches nothing of the user's. `install_antigravity` (`agy`) has no such flag: agy only discovers hooks from a plugin, so piki writes one shared, inert-without-`PIKI_CLI_AGENT` plugin into agy's own root (`~/.gemini/config/plugins/piki-multi-bridge/`) and lets the per-tab FIFO path ride the env instead. Adding a third agent = a new `install_*` module + an `AgentBridge` variant; the spawn sites and the UI need no changes. `status_severity(status, attention)` is the shared precedence rule (permission > unseen news > running) both frontends use for per-workspace/family agent rollups — the TUI re-exports it as `agent_status_severity`, the desktop mirrors it in `types.ts::agentStatusSeverity`; change all three together. `CliAgentStatus` serializes kebab-case (`waiting-permission`), matching the desktop frontend's TS union. `CliAgentState.run_started_at` (set on session start / prompt submit, cleared on stop; survives a daemon re-attach via the session snapshot) feeds the elapsed-time suffix both Agents panes show — `format_elapsed` here, mirrored by `formatElapsed` in the desktop's `types.ts`. E2E (ignored by default, drives the real binary): `crates/core/tests/cli_agent_antigravity.rs`.
- `agent_state_detect.rs` — Passive status classification for providers with no hook bridge (Codex, Muse): matches a provider's OSC window-title spinner glyphs and known blocking-prompt text against a static `StateManifest` instead of an in-band protocol. Blocked needles outrank the spinner — Muse keeps its title spinner running behind approval dialogs. Writes into the same `ShellTabState.cli_agent` field the hook bridges populate, so the Agents pane needs zero provider-specific rendering logic.
- `idle_watcher.rs` — Per-tab `IdleWatcher` for provider tabs (Custom providers). Replaces the inline byte-poll heuristic that used to live in the TUI's event loop; now shared by TUI and Desktop. Threshold is per-provider (`ProviderConfig.idle_threshold_secs`). Steps aside automatically for tabs whose `cli_agent` channel has reported, so a bridged agent never double-fires.
- `shell_env.rs` — `user_login_env()` (cached) captures the user's shell environment for GUI launches (.app/.desktop) that inherit a stripped env. **Fast path:** when stdin is a TTY (the normal TUI case) it returns `std::env::vars()` directly — spawning an interactive login shell (`-l -i -c`) to re-capture the env costs ~0.5–1s at startup (it sources the whole `~/.zshrc`) and is redundant when we were launched from a terminal. GUI launches have no TTY and take the shell round-trip. Force the round-trip with `PIKI_FORCE_LOGIN_ENV=1`.
- `search.rs` — `project_search()`: literal content search under a root via `rg` (grep fallback), returning `SearchMatch { path, line_num, text }` rows. Backs the desktop's Search-in-Project command and the TUI's `prefix-t` overlay. `list_files(root, cap) -> FileIndex { files, truncated }`: the gitignore-aware file index (`ignore::WalkBuilder`, `require_git(false)`, hidden kept, `.git` pruned, symlinks not followed, `FILE_INDEX_CAP` = 50k) behind the desktop file finder (`Ctrl+F`), memoised per workspace on the desktop side. The TUI's fuzzy search keeps its own streaming nucleo walk.
- `git.rs` — Low-level git helpers via `tokio::process::Command`. The desktop git panel's parsing lives here with unit tests: `BranchInfo` + `parse_branch_list` (`BRANCH_LIST_FORMAT`; locals first, remotes without a local counterpart, `<remote>/HEAD` skipped), `list_branches`, `last_commit_message`, `parse_ahead_behind`, `pull_summary`.
- `github/` — `gh` CLI wrappers for PR operations and unified diff parsing. `mod.rs` has the original per-checkout API (`get_pr_for_branch`/`get_pr_files`/`submit_review`, all keyed off a `current_dir` checkout) plus number-explicit variants that work against a detached-HEAD worktree (`get_pr_view`, `get_pr_files_by_number`, `submit_review_by_number`) — TUI's ad-hoc review flow uses the latter; Desktop still uses the former. `pr_list.rs` — `list_relevant_prs()` categorizes PRs relevant to the current `gh` user (authored / interacted-with / review-requested-pending) via four parallel `gh search prs` calls, with an exact "was I asked to review" check against the issue timeline API for already-interacted PRs. `checkout.rs` — `ReviewCheckoutManager::ensure_pr_checkout()` does an idempotent checkout of a PR into an app-managed directory (one shared base clone per repo + one `git worktree` per PR): reuses as-is if the local HEAD already matches the PR's remote head and the tree is clean, fetches+resets in place if stale/dirty, clones fresh only if no usable worktree exists yet (`plan_checkout()` is the pure decision function). Reused by `WorkspaceManager::create_review_workspace()` to turn a resolved checkout into an ephemeral `WorkspaceInfo` (`workspace_type = Simple`, `ephemeral = true`) — see `paths.rs::review_checkouts_dir()` and `domain.rs::WorkspaceInfo.ephemeral`.
- `session/` — Persistent sessions (design: `docs/persistent-sessions.md`). `protocol.rs` is the daemon⇄client wire format: `[kind u8][len u32 LE][payload]` frames, JSON for control messages (`Request`/`Reply`/`SessionInfo`/`ShellStateSnapshot`, every field `#[serde(default)]` so additive changes stay compatible; bump `PROTOCOL_VERSION` for anything else), raw bytes for `Input`/`Output`/`Restore`. `restore.rs` wraps the vendored vt100's `Screen::restore_formatted()` (scrollback + screen + alt screen + modes) and owns its round-trip tests — keep them green when touching `vendor/vt100`. `ShellTabState::snapshot()/from_snapshot()` (shell_integration) and the serde derives on `ShellEvent`/`CliAgentEvent` exist for this protocol. `pty::launch_plan_for_session(.., session_id)` pins the cli-agent FIFO name to `cli-agent-<session-id>.sock` so the daemon-owned FIFO outlives the frontend. `session::sessions_enabled(config_path)` is a minimal `[sessions].enabled` lookup (default true on any failure) — the file layer of `app_settings::resolve`, which the desktop calls instead of this directly; the TUI answers the same question through its full config parse, so keep the two consistent.
- `paths.rs` — `DataPaths` struct centralizing all directory paths. `sessions_dir()/session_socket()/session_lock()/session_pid_file()/session_log_path()` are the session daemon's; `session_socket()` is always `<data-dir>/sessions/daemon.sock`. The `sun_path` (~108B) cap on an overflowing socket path is handled at the `bind`/`connect` syscall by `session::uds` (daemon `chdir`+bind while single-threaded; client dials `/proc/self/fd/<dirfd>/daemon.sock` on Linux, mutex-guarded `chdir` elsewhere) — the socket file is never relocated out of the data dir.
- `sysinfo.rs` / `preflight.rs` — Runtime environment checks.

## Conventions

- Error handling: `anyhow::Result` for application errors.
- Thread safety: `parking_lot::Mutex<Connection>` for SQLite, traits are `Send + Sync`.
- Schema changes: add migration in `sqlite.rs`, bump version constant.
- Storage traits: add new trait in `mod.rs`, implement in `sqlite.rs`, wire through `AppStorage`.
- All public types that cross crate boundaries go in `domain.rs`.
